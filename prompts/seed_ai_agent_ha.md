# ai_agent_ha Companion Integration — Awareness and Diagnosis

Trigger: ai_agent_ha installed, AI-created automation broken, ai_agent_auto_ automation not
working, phantom entity state, set_entity_state wrong value, LLM-created dashboard broken,
automations.yaml.bak exists, state mismatch after ai_agent_ha action

## Context

`ai_agent_ha` (HACS, domain `ai_agent_ha`) is a sidebar LLM chat panel that runs **inside** HA
and can create automations, dashboards, and call services. Pueo acts as a safety net for
changes it makes.

## Key behavioural quirks

### 1. AI-created automations use a recognisable id prefix

Automations created by `ai_agent_ha` have ids starting with `ai_agent_auto_`
(e.g. `automation.ai_agent_auto_turn_off_lights`). When diagnosing a broken automation,
if the id starts with this prefix it was most likely generated by ai_agent_ha.

### 2. `automations.yaml.bak` is created before each automation write

`ai_agent_ha` writes a backup of `automations.yaml` to `automations.yaml.bak` before
modifying it. If an AI-generated automation breaks things, restoring from this file is
the first recovery step:
- Read `/config/automations.yaml.bak` with `read_file` and compare with the current
  `/config/automations.yaml`.
- If the current file contains an obvious error that was absent in the backup, restore it.

### 3. No `check_config` before `automation.reload`

`ai_agent_ha` does not call `ha core check` before reloading automations after writing.
This means a YAML error in a generated automation can reload into an invalid state.
Always run `ha core check` (via `run_ha_command`) before and after any automation repair.

### 4. `set_entity_state` creates phantom state for non-standard domains

`ai_agent_ha`'s `set_entity_state` service maps the following domains to real HA service
calls: `light`, `switch`, `cover`, `climate`, `fan`. For **every other domain**, it falls
back to `hass.states.async_set`, which updates the state cache **without touching the
underlying device**. This creates phantom state that:
- Reports the "set" value in HA until the next real state update from the device.
- Does not survive HA restart (the device's actual state is restored).
- Can cause Pueo lovelace diagnostics to flag entities as having unexpected state values.

When diagnosing a state mismatch on a domain not in the list above, check whether
ai_agent_ha was recently active (`get_logbook` filtered to `ai_agent_ha`).

## Diagnosis recipe

1. `get_ha_profile field="installed_integrations"` — confirm `ai_agent_ha` is present.
2. `get_logbook(entity_id="", start_time="<window>")` — look for `ai_agent_ha` service
   calls (`create_automation`, `create_dashboard`, `update_dashboard`, `set_entity_state`).
3. For a broken automation with `ai_agent_auto_` prefix:
   a. `get_automation_traces(entity_id="automation.ai_agent_auto_<name>")` — find failure.
   b. `read_file("/config/automations.yaml")` — check for YAML error.
   c. `read_file("/config/automations.yaml.bak")` — compare with backup.
   d. `run_ha_command("ha core check")` — confirm config validity.
4. For phantom entity state on a non-standard domain:
   a. `get_entity_history(entity_id=...)` — does the value match recent service calls?
   b. `get_logbook(entity_id=...)` — find the `set_entity_state` call from ai_agent_ha.
   c. Note in the repair report that the state was set by ai_agent_ha without device contact;
      real state will restore on next device update or HA restart.
5. `remember(key="ai_agent_ha_quirk", content="<specific finding>")` — record any
   instance-specific pattern (e.g. "user creates automations for media_player domain via
   ai_agent_ha — expect phantom state").
