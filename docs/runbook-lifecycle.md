# Pueo — Runbook Lifecycle

How Pueo learns runbooks: atomic entries, family scope, the procedural and verdict distillation lanes, runbook states, session verification, and the distillation prompt. Moved out of `docs/key-patterns.md` (#1109) so the auto-loaded patterns file stays under the memory-file size limit. See ADR 038, 044, 046, 049, 050, 051, 052.

Learned knowledge is stored as atomic rows in `runbook_entries` (V42/V44, ADR 051/052): `kind` is `decision_rule`, `pitfall` or `procedure`, and each row carries `episode_refs` plus `success_count`/`failure_count`. Rows are inserted or reinforced (a near-duplicate adds a success and an episode ref, once per episode), never rewritten. `render_learned_runbook()` rebuilds the signature's candidate/validated `agent_strategies.approach` from the live rows: title `Learned: <sig>`; sections `## Decision rules`, `## Pitfalls`, `## Procedure notes` (last). It keeps the row's state and syncs Chroma via `sync_strategy_to_chroma`, with signature metadata. With no live rows the runbook is discarded. A verdict write therefore never erases procedure notes.

**Family scope (ADR 052):** `_write_entries` receives `subject_tokens` (last segment of the signature + `subject_key`). Items whose text contains none of those tokens are written under the *family pattern* — the signature with its last segment replaced by `*` (e.g. `update:addon:*`). After writing a concrete entry, `_promote_siblings_to_family` checks for near-dup entries in sibling signatures (same prefix, different last segment) and merges them into the family-pattern entry (summed counts, retired subject rows with `promoted_to`). Retrieval (`_fetch_signature_chunks`) reads live entries from both the exact signature and the family pattern, renders them via `_render_approach`, and builds the chunk in-memory — the `agent_strategies` row is still kept for Chroma / `/runbooks` but is no longer the retrieval source for the learned chunk. `_auto_validate_if_eligible` counts verified successes across all sibling signatures when the strategy signature ends with `:*`.

Two distillation lanes run after a session ends:

**Procedural lane (ADR 049, ADR 051):** Fires for any session that reached a conclusion (`success`, `needs_action`, `monitoring` or `awaiting_approval`), never for `failed`/`stuck`. There is no LLM: `extract_procedure_facts` records failed calls with normalised errors, corrected retries, identical repeats and empty results as `procedure` entries (exact-text dedup, render cap 8). Each (tool, problem) is also counted in `user_prefs` `procedure_quirk:<hash>` rows, and the top ones are shown on `/runbooks` (#991). If the signature has no learned runbook yet, a procedure-only candidate is rendered. Notes are pre-injected as a separate `[PROCEDURE NOTES]` chunk; a procedure-only runbook emits no body chunk. The lane is `distill_procedure()` in `utils/knowledge/runbook_distiller.py`, enqueued via `enqueue_procedural_distillation()`. It does **not** stamp `distilled_at`.

**Verdict lane (ADR 044/046/051):** Fires after explicit verification: the user clicks "Pueo was right" or "got this wrong", or a system verifier marks success/failure. The LLM returns `DistilledDelta{decision_rules, pitfalls, instance_facts}` (items cite `evidence_step`; no title or tool list). `_gate_item` drops an item, logged as `distillation_entry_rejected reason=…`, when it is:
- ungrounded in the whole trace plus the correction (`_fact_is_grounded`)
- ≥60% covered by the seed (`_overlaps`, framing words ignored)
- carrying a version string while the seed is a wildcard or absent
- naming an unregistered tool (`_unknown_tools`)

Kept items become `decision_rule`/`pitfall` entries (`distillation_entry_written`). A failure verification with a correction first adds 1 to `failure_count` on the verdict entries created at or before the session started (the ones it was shown), and retires an entry at failure ≥ success+1. The entry points are `distill_and_persist()` / `enqueue_distillation_after_verification()`. Stamps `distilled_at` on every terminal path.

Three runbook states: **seed** (human-curated, per-symptom with a `signature:` in front matter, embedded at RAG refresh via `strategy_seeder.py`), **validated** (promoted automatically after `RUNBOOK_VALIDATE_MIN_SUCCESSES` verified successes with no failures), and **candidate** (auto-distilled from a verdict or procedural session, awaiting review). Procedure-only candidates do not auto-promote — `_auto_validate_if_eligible` requires `runbook_usage.verification='success'` rows. Non-success sessions produce a row in `knowledge_gaps` (never retrieved by agents — developer-facing only).

Seeds are one file per symptom with wildcard signatures (`repair:*:restart_required`). `_fetch_signature_chunks` returns both the matching seed and the best learned runbook, each up to 1 200 tokens uncut.

The `/runbooks` tab opens with a **Learning health** table (`SignatureStats` from `kb_meta_analyzer._load_signature_stats`): per signature, sessions (30 d), verified/pending/unverified counts, matched seed, best learned state, procedure-note and instance-fact counts, last session/use, plus a collapsed list of seeds no session has matched. Rows with recent sessions but no verification and nothing learned are highlighted.

Session outcomes (`session_outcomes` table): every non-chat AgentLoop session writes a row with `distill_payload_json` stashed for later. System verifiers mark rows `success`/`failure`: the repair reconcile loop, the update install result (auto and manual), and `_verify_card_execution` in the `ha_command`/`service_call`/`config_entry_reload`/`automation_create`/repair-fix card executors. The **"Pueo was right"** button (`/right/{nid}`) marks `success`, and **"Pueo got this wrong"** marks `failure` and stores a correction. **Prediction checks (ADR 050):** `finish_device_availability`/`finish_host_health` may end with a `prediction` (`recovers_without_action`|`recovers_after_reload`|`stays_offline`, `within_minutes`) stored in `conclusion_json`; the device poll (`check_device_predictions`) and host-health poll (`verify_host_health_sessions`) judge it with `judge_prediction()` in `utils/knowledge/session_verification.py` and mark the session `success`/`failure` by `system` (failures get an auto correction). An unpredicted recovery still verifies nothing, and a cleared host-health finding counts only via its prediction or a session action, never for `unexpected_reboot`. A daily `verification_digest` card (`VERIFICATION_DIGEST_HOUR`, from the `backup_sync` loop) lists open verification questions via `/right`, `/wrong`, `/off`. A re-sent card nid supersedes older pending rows for that `card_id` (payload cleared, out of stats and the hold). A session sending a card with its `episode_id` defers (`ToolExecutor._mark_card_queued`); `awaiting_approval` writes no gap. `enqueue_distillation_after_verification` is called after each resolution: it reads the stashed payload, fetches the matching seed text, and submits a PRIORITY_LOW WorkItem. Failure rows without a correction are never distilled. Unresolved rows are swept to `unverified` after 48 h (payload cleared), unless the session's HITL card is still open (`session_outcomes.card_id`, or the card payload's `episode_id`); those rows are held up to 14 days and never distilled. `session_outcomes.distilled_at` (V41) is stamped on every terminal distillation path, so startup recovery and repeat enqueues skip distilled sessions.

The distillation prompt is **signature-scoped** (not "most general"). It includes the matched seed, the already-learned entries and the correction when present, and asks only for the delta: decision rules and pitfalls not already there. Empty lists are the expected answer when the session confirms the seed. `instance_facts` each cite an `evidence_step`; facts not grounded in that step's output are dropped (`_fact_is_grounded`). Surviving facts are upserted into `agent_memory` with the session signature (pre-injected as `[INSTANCE FACT]`), even when no entry is written. A `runbook_followed` id without its `seed:` prefix is normalized before the `runbook_usage` write. `repair_history` embedding only embeds verified episodes.

`seed_home_profile()` in `strategy_seeder.py` generates a dynamic `ha_instance_profile` document and upserts it into the `strategies` ChromaDB collection at each RAG refresh (step 5.5). `prompts/seed_supervisor_cli.md` provides a Supervisor CLI reference; `TestPromptCommandAllowlist` fails if any prompt recommends a `run_ha_command("…")` the allowlist rejects. Only `seed_*.md` files are seeds; other agents' system prompts are `_RETIRED_SEED_PROMPTS` and are purged. `TestSeedRegistry` fails when a `seed_*.md` is neither registered nor retired, or when a seed's `signature:` matches no signature the `sig_*` functions produce for a canonical trigger table (dead seed). Signature parts map `-` to `_` (`http-login` → `notification:http_login`); HACS repository updates are signed `update:hacs_integration:<slug>` (`classify_update_type`). Integration setup (new flow, re-enable, re-add) is signed `setup:integration:<domain>` (`sig_setup`). The generic method is `seed_setup_integration.md` (`setup:integration:*`); per-domain verdicts live in seeds such as `seed_setup_noaa_it_all.md` (#1071). **Seeds own verdicts:** `agent_loop_*.md` keep the method, tool mechanics, safety rules and the grounding rule ("never state a fact that does not appear in a tool output"); per-type "conclude X" rules live in signature-matched seeds, and `TestPromptNoVerdictRules` guards against them coming back. The startup step rewrites legacy signatures (`normalize_legacy_signatures`) and re-seeds changed seeds. Pre-inject (`_format_knowledge_block`) head-truncates each chunk to its own budget in rank order; investigation callers pass a targeted `knowledge_query`. See ADR 044, ADR 046.
