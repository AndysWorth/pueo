# Runbook Lifecycle — Design Specification

> This spec supports ADR 038. It is the reference for S4–S7 implementation.
> Updated in place as decisions are refined.

## 1. Symptom signatures

A **signature** is a deterministic string derived from the session's structured initial
context. It is the single key for dedup, gap merging, usage stats, and resolution.
Signatures are computed by pure functions in `utils/knowledge/runbook_signature.py`.

### Grammar

```
<signature> ::= <type> ":" <part1> [":" <part2>]
```

### Per session type

| Session source           | Function                                    | Signature example                                     |
| ------------------------ | ------------------------------------------- | ----------------------------------------------------- |
| Repair issue             | `sig_repair(domain, translation_key)`       | `repair:recorder:backup_not_available`                |
| HA Core update           | `sig_update("core", "homeassistant")`       | `update:core:homeassistant`                           |
| HAOS update              | `sig_update("os", "homeassistant")`         | `update:os:homeassistant`                             |
| Add-on update            | `sig_update("addon", slug)`                 | `update:addon:mosquitto`                              |
| HACS update              | `sig_update("hacs", slug)`                  | `update:hacs:lovelace-mushroom`                       |
| Live log error           | `sig_log(logger, exception_class)`          | `log:homeassistant.components.recorder:DatabaseError` |
| Lovelace entity          | `sig_lovelace(entity_domain, failure_kind)` | `lovelace:sensor:unavailable`                         |
| Persistent notification  | `sig_notification(id_prefix)`               | `notification:update_all_package`                     |
| Chat (runbook retrieved) | `sig_chat(top_sig)`                         | `chat:repair:recorder:backup_not_available`           |
| Chat (nothing retrieved) | `sig_chat(None)`                            | `chat:unclassified`                                   |

**Sanitisation rules** (applied in `_sanitize(s: str) -> str`):

- Lowercase everything
- Replace spaces and slashes with `_`
- Strip non-alphanumeric except `_` and `:`
- Truncate each component to 64 characters
- If any required input is empty or `None`, substitute `unknown`

### Input sources

| Session type | Where signature inputs come from |
|---|---|
| Repair | `domain` and `translation_key` from the repair issue payload |
| Update | `update_type` from `UpdateTarget.kind`; `slug` from `UpdateTarget.slug` |
| Log | `logger` field from the log line; `exception_class` from `LogEvaluation.exception_class` or `"none"` |
| Lovelace | `entity_domain` from the entity id; `failure_kind` from the card trigger reason |
| Notification | `notification_id` prefix before the first `.` or `_` separator |
| Chat | The signature of the highest-authority runbook returned by the first `query_knowledge` call |

`AgentLoop` receives the signature at construction time via a `signature: str`
parameter. Callers compute it before constructing the loop. The `signature` is stored
on the loop and on the debug episode row.

## 2. Runbook schema

All newly created runbooks use this schema. Existing seed prompt files (in `prompts/`)
continue to be seeded as prose until they are regenerated by distillation.

### Frontmatter (YAML)

```yaml
---
signature: repair:recorder:backup_not_available
domain: recorder
integrations: []              # optional list of HA integration slugs
ha_version_min: ""            # earliest HA version this applies to, e.g. "2025.1.0"
ha_version_max: ""            # latest HA version, empty = current
recommended_tools:            # ordered tool names for Phase 3 evidence gathering
  - read_logs
  - run_ha_command
state: candidate              # seed | candidate | validated
version: 1                    # monotonically increasing integer, bumped on merge
episode_refs:                 # list of debug episode ids that informed this runbook
  - 9f3a...
---
```

### Body sections

```markdown
## When to use
Trigger conditions and symptoms — when should Phase 1 retrieval surface this runbook?

## Hypotheses → evidence
For each hypothesis: what to look for and which tool calls confirm or refute it.

## Root-cause tests
Explicit pass/fail checks to run before acting (e.g. "if `recorder.db` > 2 GB, this is
a disk-space problem, not a connection problem").

## Fix
Ordered steps. Include the backup-before-write ordering where a write is involved.

## Verification
How to confirm the fix worked (specific command output or state to check).

## Pitfalls
Known failure modes for this approach, with remediation notes.
```

All sections are required for distilled runbooks. Seed prose runbooks that lack the
frontmatter are seeded with `signature: seed:<filename>` and `state: seed`.

### 2.1 How signatures are used in retrieval

The `signature` field is stored as Chroma metadata on every `strategies` embedding.
`_pre_inject_knowledge` runs two lookups before the session's first LLM call:

1. **Exact signature lookup** — `collection.query(where={"signature": sig}, n_results=1)`.
   If a hit is found, that runbook is injected regardless of its cosine score. This
   guarantees the canonical recipe for this exact symptom always surfaces.

2. **Semantic search** — the existing BM25+cosine hybrid over the full `strategies`
   collection, using the session's natural-language trigger as the query. This finds
   related but non-identical runbooks (e.g. other `repair:recorder:*` entries when the
   current signature is `repair:recorder:migration_failed`).

Results from both lookups are merged and deduplicated by Chroma id before injection.
The exact-match hit is always placed first so it is read before broader context.

`query_knowledge` calls made by the model during the session continue to use semantic
search only — the model frames questions in natural language, not signatures.

## 3. Distillation qualifying rule

A session **qualifies** for candidate distillation when all three hold:

1. `outcome == "success"`
2. `evidence_tool_calls >= 3` (tool calls excluding terminal tools and `query_knowledge`)
3. Either:
   - No `agent_strategies` row with a matching `signature` exists, **or**
   - The session's tool sequence diverged from the stored `recommended_tools` (Jaccard
     similarity < 0.6)

A session qualifies for **gap distillation** when:

- `outcome in ("failed", "stuck")`, **or**
- `outcome == "success"` but `_query_knowledge_had_results == False` and the session
  called `query_knowledge` at least once

When neither candidate nor gap conditions are met (short successful session on a known
signature with matching tools) no distillation WorkItem is enqueued.

## 4. The distillation WorkItem

`AgentLoop.run()` calls, at session end:

```python
queue = get_work_queue_or_none()
if queue and qualifies_for_distillation(session):
    queue.enqueue(WorkItem(
        fn=distill_session,
        args=(session_snapshot,),
        priority=PRIORITY_LOW,
        activity_type="runbook_distill",
        dedup_key=f"distill_{signature}",
    ))
```

`session_snapshot` is a lightweight frozen copy of the episode data (tool calls, outcome,
signature, episode_id) created synchronously before the queue call. No mutable state
is shared with the live loop.

`distill_session(snapshot)` makes **one** structured LLM call:

- `temperature=0`, `format=DistilledRunbook.model_json_schema()`
- System prompt from `prompts/runbook_distiller.md`
- User content: the episode's `tool_calls` sequence (name + args + outcome) truncated
  to `MAX_PROMPT_TOKENS`
- Output: `DistilledRunbook` Pydantic model, validated before any write

## 5. Merge semantics

After distillation produces a `DistilledRunbook`, the distiller decides merge vs. insert:

### Merge condition (any of)

- An `agent_strategies` row with the same `signature` exists
- A Chroma chunk from `strategies` has cosine similarity ≥ 0.92 to the new runbook text

### Merge behaviour

- `version` is incremented
- `episode_refs` is extended with the new episode id (capped at 20 most recent)
- `recommended_tools` is updated if the new sequence is longer (more evidence)
- `approach` body is replaced with the new distilled text (more recent wins)
- `state` is unchanged — a candidate stays candidate, a seed stays seed
- Chroma is updated in place (same id) via `sync_strategy_to_chroma`

### Insert behaviour (no match)

- New row in `agent_strategies` with `state = "candidate"`, `version = 1`
- Embedded into Chroma under `strategies` collection
- `runbook_usage` will start tracking from the first retrieval

---

## 6. Gap semantics

Gaps are written when `outcome != "success"` or when retrieval found nothing. The
distiller calls `write_gap(signature, snapshot)`:

- **Merge:** if `knowledge_gaps` already has a row with the same `signature`, extend
  `episode_ids`, update `gap_description` and `queries_tried` (keep most recent).
- **Insert:** new row with `resolved_at = NULL`.

Gaps are **never** embedded into the `strategies` collection and **never** returned by
`query_knowledge`. They appear only in the dashboard `/runbooks` gaps panel.

**Auto-resolution:** when a qualifying candidate distillation succeeds for a signature
with an open gap:

```python
resolve_gap(signature, episode_id=new_candidate_episode_id)
```

Sets `knowledge_gaps.resolved_at = now()` and
`knowledge_gaps.resolved_by_episode_id = episode_id`.

## 7. Validation thresholds

| Parameter | Default | Config key |
|---|---|---|
| Successes required for auto-validation | 3 | `RUNBOOK_VALIDATE_MIN_SUCCESSES` |
| Failures that trigger a dashboard warning | 2 (with 0 successes) | hardcoded constant |
| Merge cosine threshold | 0.92 | hardcoded constant (revisit if false merges appear) |
| Jaccard divergence threshold | 0.60 | hardcoded constant |
| Max episode refs per runbook | 20 | hardcoded constant |
| Distillation min evidence tool calls | 3 | hardcoded constant |

**Auto-validate trigger** (called in `runbook_usage` write path at session end):

```python
if (
    successes_on_distinct_episodes(strategy_id) >= RUNBOOK_VALIDATE_MIN_SUCCESSES
    and failures(strategy_id) == 0
    and current_state == "candidate"
):
    promote_to_validated(strategy_id)
    sync_strategy_to_chroma(strategy_id)
```

Only the `candidate → validated` transition is automatic. `validated → seed` requires a
human action in the dashboard. Discarding (`candidate → discarded`) also requires human
action and deletes the Chroma embedding.

## 8. Session-type construction checklist

When wiring a new `AgentLoop` call, the caller must:

1. Compute the signature via the appropriate `runbook_signature.*` function before
   constructing the loop.
2. Pass `signature=sig` to `AgentLoop.__init__`.
3. Confirm the loop's `ToolExecutor` receives `knowledge_store` (so pre-injection and
   usage recording work).
4. Confirm the loop is constructed inside or after `PueoWorkQueue` is initialised (so
   distillation WorkItems can be enqueued).

## 9. Collection membership

| Collection | In `COLLECTIONS` (queried by `query_knowledge`) | Purpose |
|---|---|---|
| `strategies` | Yes | Seed, candidate, validated runbooks |
| `knowledge_gaps` | **No** | Gap analytics + dashboard display only |
| `repair_history` | Yes | Past repair episode summaries |
| `ha_release_notes` | Yes | HA changelog |
| `ha_integration_docs` | Yes | HA integration docs |
| `ha_concepts` | Yes | Official HA developer docs |
| `ha_developer_docs` | Yes | Developer reference |
| `ha_best_practices` | Yes | homeassistant-ai/skills reference |

`knowledge_gaps` is created at startup by `ChromaKnowledgeStore.__init__` alongside
the other collections, but it is **not** added to the `COLLECTIONS` list.
